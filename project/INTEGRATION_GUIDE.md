# Инструкция: PostgreSQL и Langflow для чата студентов

Документ описывает подключение PostgreSQL и Langflow к приложению на FastAPI.
PostgreSQL используется для пользователей и работ. Сообщения чата передаются
из backend в Langflow, где flow `tutor-flow` выполняет поиск по PostgreSQL;
история чата приложения пока хранится только в памяти процесса.

Flows хранит flow, которые используются в langflow; custom_components хранит кастомные компоненты этих flow. Langflow развёрнут через docker compose на 103.73.35.132. tg_bot.py содержит пример интеграции с langflow.

## 1. Подготовить PostgreSQL

1. Создать базу и пользователя приложения. Выдать пользователю только права,
   необходимые приложению: подключение к базе, чтение и изменение нужных таблиц.
2. Убедиться, что таблицы и связи соответствуют схеме проекта:

   | Таблица | Используемые поля |
   | --- | --- |
   | `users` | `id`, `email`, `username`, `role`, `telegram_id`, `password_hash` |
   | `submissions` | `id`, `student_id`, `file`, `status`, `created_at` |
   | `chat_sessions` | `id`, `user_id`, `created_at` |
   | `messages` | `id`, `session_id`, `sender`, `text`, `created_at` |
   | `feedbacks` | `id`, `text` |
   | `grades` | `id`, `student_id`, `submission_id`, `feedback_id`, `final_score`, `graded_by`, `created_at` |

   Внешние ключи должны связывать `submissions.student_id` и
   `chat_sessions.user_id` с `users.id`, `messages.session_id` с
   `chat_sessions.id`, а `grades` — с соответствующими пользователями,
   работами и отзывами. Для имён пользователей нужен уникальный индекс.

3. Проверить ограничения столбцов:
   - текущая регистрация не передаёт `email`; если `users.email` обязателен и
     не имеет значения по умолчанию, добавить email в форму и модель регистрации
     либо сделать поле допускающим `NULL`;
   - `submissions.file` должен вмещать JSON с именем файла и извлечённым текстом
     PDF/DOCX, например иметь тип `TEXT`, а не короткий `VARCHAR`;
   - текущая запись оценки передаёт `NULL` в `grades.final_score`, поэтому
     столбец должен допускать `NULL`;
   - приложение использует статусы работ `На проверке`, `На доработке`,
     `Проверено`.

4. Настроить локальное подключение:

   ```powershell
   Copy-Item .env.example .env
   ```

   Заполнить в `.env`:

   ```dotenv
   DB_HOST=
   DB_PORT=5432
   DB_NAME=
   DB_USER=
   DB_PASSWORD=
   ```

   Файл `.env` содержит секреты и не должен попадать в Git. В проекте уже есть
   `psycopg2-binary`; `main.py` загружает `.env` и подключается через
   `get_db_connection()`.

5. Установить зависимости и запустить приложение из корня проекта:

   ```powershell
   py -m pip install -r requirements.txt
   py -m uvicorn main:app --reload
   ```

   Проверить `/login`, регистрацию студента и вход преподавателя. Преподавателя
   создавать вручную в БД. Важно: текущий код сверяет
   `password_hash` с `SHA-256(password).hexdigest()`; созданная вручную запись
   должна совпадать с этим форматом. Для production перед запуском следует
   заменить SHA-256 на специализированный алгоритм хранения паролей и
   предусмотреть миграцию существующих хэшей.

### Что приложение уже сохраняет

- Регистрация и вход используют таблицу `users`.
- Работы сохраняются в `submissions`. В текстовом поле `file` хранится JSON:
  `{"filename": "...", "content": "извлечённый текст"}`.
- Решение преподавателя меняет `submissions.status`; комментарий пишется в
  `feedbacks` и связывается с работой через `grades`.
- Страница преподавателя показывает количества работ по статусам.

Не менять формат поля `submissions.file`, не согласовав это с парсером в
`main.py`.

## 2. Подготовить Langflow

1. Запустить Langflow и создать flow для текстового диалога: вход чата,
   необходимые узлы модели/логики и выход чата.
2. Проверить flow в интерфейсе Langflow на обычном сообщении.
3. Скопировать ID flow и создать API key. Не помещать ключ в браузерный JavaScript
   и не отправлять его пользователю.
4. Добавить в `web_site/.env` настройки интеграции:

   ```dotenv
   LANGFLOW_BASE_URL=http://localhost:7860
   LANGFLOW_FLOW_ID=
   LANGFLOW_API_KEY=
   LANGFLOW_TIMEOUT_SECONDS=30
   ```

   `LANGFLOW_BASE_URL` по умолчанию равен `http://localhost:7860`, а таймаут
   `30` секунд. Для запуска в Docker укажите адрес Langflow, доступный именно
   из контейнера приложения. `.env.example` содержит шаблон без реального ключа.

5. Проверить запуск flow напрямую. В актуальной документации Langflow описан
   endpoint `POST /api/v1/run/{flow_id_or_name}?stream=false` с API key в
   `Authorization: Bearer ...` и телом запроса примерно такого вида:

   ```json
   {
     "input_request": {
       "input_type": "chat",
       "input_value": "Проверочное сообщение",
       "output_type": "chat",
       "session_id": "test-session",
       "user_id": "test-user"
     }
   }
   ```

   Формат API может отличаться между версиями Langflow. Сверить endpoint,
   заголовок авторизации и форму ответа с API docs именно установленного
   экземпляра и с примером API, который он генерирует. Официальная справка:
   <https://docs.langflow.org/api>.

## 3. Подключить Langflow к endpoint чата

Текущий интерфейс отправляет `POST /api/chat` с JSON `{"message": "..."}` и
ожидает JSON `{"response": "ответ"}`. Endpoint проверяет сессию и роль
студента, затем backend отправляет запрос в Langflow с `user_id` и стабильным
для пользователя `session_id`. При ошибке Langflow endpoint возвращает
контролируемую ошибку, а не фиктивный ответ. Не менять frontend-контракт без
одновременного изменения `static/chat.js`.

В `main.py` заменить заглушку `get_ai_response(text)` на серверный вызов
Langflow:

1. Вызвать API из backend, используя `LANGFLOW_BASE_URL`, `LANGFLOW_FLOW_ID` и
   `LANGFLOW_API_KEY`; ключ не передавать в HTML или JavaScript.
2. Отключить streaming для текущего frontend-контракта. Установить сетевой
   timeout, проверить HTTP status, разобрать ответ Langflow и вернуть из функции
   обычную строку. Не возвращать заглушку при ошибке: endpoint должен сообщить
   об ошибке сервиса, а frontend покажет её студенту.
3. Добавить HTTP-клиент в `requirements.txt`, если выбранная библиотека ещё не
   установлена. Для асинхронного `/api/chat` использовать асинхронный клиент
   либо выполнять блокирующий вызов в thread pool.
4. Не передавать в Langflow доверенную историю, полученную от браузера. Историю
   читать из PostgreSQL для текущего пользователя и активной сессии.

### Сохранять историю чата в БД

Сейчас `GET /chat` и `POST /api/chat` используют словарь `chat_histories`;
перезапуск приложения очищает историю. Для постоянного хранения использовать
уже имеющиеся `chat_sessions` и `messages`:

1. По `session["user_id"]` найти активную сессию пользователя в
   `chat_sessions`; если её нет — создать строку и получить `id`.
2. При `GET /chat` прочитать сообщения по `messages.session_id`, упорядочив по
   `created_at` и `id`, и передать их шаблону.
3. При `POST /api/chat` записать входной текст с `sender='user'`, вызвать
   Langflow, затем записать ответ с `sender='bot'`.
4. Использовать стабильный ID сессии как `session_id` в запросах Langflow,
   чтобы его механизм памяти связывал ходы диалога. В Langflow также передавать
   `user_id=str(session["user_id"])`, если flow использует идентификатор
   пользователя.
5. Сохранять входящее сообщение и ответ в транзакционно понятном порядке.
   При timeout/ошибке Langflow не сохранять фиктивный ответ; вернуть
   контролируемую ошибку клиенту. Не оставлять открытые транзакции во время
   долгого сетевого запроса.

Рекомендуется добавить индексы по `chat_sessions.user_id` и
`messages(session_id, created_at)`.

## 4. Проверка перед сдачей

- Неверные DB-параметры дают понятную ошибку, а успешные подключение и запросы
  работают из приложения.
- Новый пользователь получает роль `student`; дубликат логина не создаёт
  вторую запись.
- Студент не может читать чужие сессии или отправлять сообщения без авторизации.
- Два сообщения одного пользователя в одной сессии доходят до одного Langflow
  flow с одинаковым `session_id`; ответ отображается в чате и остаётся после
  перезапуска приложения.
- Проверены timeout, недоступность Langflow, неверный API key и неожиданный
  формат ответа.
- `.env` и API key не коммитятся; в production используются TLS и отдельные
  учётные данные с минимальными правами.
